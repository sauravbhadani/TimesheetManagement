What this covers

Two diagrams for sign-off before any code is written: a component architecture (how the pieces run and talk to each other) and a workflow (how a timesheet actually moves from a blank grid to an approved record). SECTION 02

Architecture diagram

Layered API (Controllers → Services → Repositories → EF Core) behind a single auth abstraction, so the same controllers and React auth context work unmodified whether a deployment is running the seeded local login or a customer's Entra ID tenant — only Auth:Provider in config changes.

SECTION 04

Workflow — timesheet lifecycle

Four states. The only loop back is Rejected → Submitted; everything else is one-directional, and Approved is terminal for everyone except Admin (read-only override, not a state transition).

Workflow — end-to-end sequence

The request path from an employee filling in a week to a manager's decision, including the reject → resubmit loop.

sequenceDiagram
  actor E as Employee
  participant W as React SPA
  participant A as Web API
  participant D as SQL Server

  E->>W: Fill weekly grid, Save Draft
  W->>A: POST /api/timesheets
  A->>D: Upsert TimesheetWeek + Entries (Status=Draft)
  A-->>W: 200 OK

  E->>W: Submit
  W->>A: POST /api/timesheets/{id}/submit
  A->>D: Status=Submitted, SubmittedAt=now
  A->>D: ApprovalHistory += Submitted
  A-->>W: 200 OK
  Note over E,A: Grid now locked for Employee

  actor M as Manager
  M->>W: Open Team Timesheets (status=Submitted)
  W->>A: GET /api/timesheets/team?status=Submitted
  A->>D: Query direct reports' weeks
  A-->>W: List
  M->>W: Open Review Timesheet

  alt Approve
    M->>W: Approve
    W->>A: POST /api/timesheets/{id}/approve
    A->>D: Status=Approved, ApprovedBy, ApprovedAt
    A->>D: ApprovalHistory += Approved
    A-->>W: 200 OK — read-only for all but Admin
  else Reject
    M->>W: Reject + comment
    W->>A: POST /api/timesheets/{id}/reject
    A->>D: Status=Rejected, RejectionComment
    A->>D: ApprovalHistory += Rejected
    A-->>W: 200 OK
    E->>W: Edit rejected week, resubmit
    W->>A: POST /api/timesheets/{id}/submit
    Note over E,A: Loops back into Submitted
  end

SECTION 06

Auth pluggability — the design's central constraint

Everything above — controllers, services, the React auth context — is written once. Only the identity source and token-issuing path differ, selected entirely by Auth:Provider.

AspectLocal mode (default, dev)Entra ID mode (customer deployment)
Login UIDropdown of seeded test users (Admin/Manager/Employee)MSAL redirect to customer tenant
TokenLocally-issued JWT asserting Id + RoleEntra-issued JWT, bearer-validated by API
Role sourceSeed data Users.RoleEntra group / app-role claims
User provisioningPre-seededJIT — mapped to Users table on first login
Config switchAuth:Provider = "Local"Auth:Provider = "EntraId"
Downstream checks[Authorize(Roles=...)] — identical either way
SECTION 07

Build sequence, once approved

Matches the brief's incremental order (Section 8) — each layer verified before the next starts.

  1. EF Core schema + migrations + seed (Admin/Manager/Employee, sample Projects/Tasks)
  2. Web API — Controllers → Services → Repositories, validation, global error handling
  3. Local auth mode (seeded dropdown login, JWT issuance, role checks)
  4. Employee screens — weekly grid, Save Draft / Submit, My History
  5. Manager screens — Team Timesheets, Review + Approve/Reject
  6. Admin screens — Projects, Tasks, Users CRUD
  7. Branding Config (frontend-only, localStorage)
  8. Entra ID auth mode (MSAL, bearer validation, JIT provisioning) + App Insights wiring
SECTION 08

Assumptions going in

Flagging these rather than blocking on them — say if any should change

  • Week is hard-coded Mon–Sun for v1, but the boundary is read from config (not a literal switch/day-of-week check), so a future customer's fiscal week is a config change.
  • Hour validation (24h/day ceiling, 8–10h soft warning) is enforced in the Service layer as a warning, not a blocking error, matching "soft validation" in the brief.
  • TotalHours on TimesheetWeek is computed server-side on every save rather than trusted from the client.
  • One TimesheetEntry row per (Project, Task) per week — resubmitting a rejected week reuses existing rows rather than creating new ones.
  • Local-mode JWT signing key and seed users live in appsettings.Development.json, excluded from anything resembling a production config.
